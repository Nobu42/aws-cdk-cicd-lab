# インフラ設計書（AWS CDK / CI/CD検証基盤）

作成日: 2026-09-26
状態: 設計案。アプリケーション用AWSリソースとパイプラインは未実装・未デプロイ。

## 1. 目的

TypeScriptによるAWS CDKの環境別構築と、AWS Codeシリーズによるアプリケーションのビルド・テスト・デプロイを検証する。
Gitの変更管理、設定差分の確認、失敗時のログ調査、切り戻し、削除までを実践する。

元設計: [terraform-iac-lab インフラ設計書](https://github.com/Nobu42/terraform-iac-lab/blob/main/docs/Design_Specification.md)

本書は元設計のネットワーク・Web基盤を流用した別環境の設計である。元リポジトリの設計・既存リソースは変更しない。学習上の本番想定環境は実業務の本番環境ではない。

## 2. 元設計からの変更

| 項目 | 元設計 | 本設計 |
| --- | --- | --- |
| 基盤構築 | AWS CLI / ShellからTerraformへ移行 | CDK v2 / TypeScript |
| 管理範囲 | 既存ラボ | 独立したCloudFormationスタックと専用リソース |
| 名前 | sample系 | `cdk-cicd-lab-<stage>`を接頭辞に使用 |
| ネットワーク | 2AZ、Public / Private、AZごとのNAT | 論理構成を流用 |
| Web | Private EC2 2台、ALB、ポート3000 | 配置と通信経路を流用。最初はDB不要の小さなWebアプリ |
| アプリ配布 | Ansible等 | CodeBuildで成果物を作成し、CodeDeployで配布 |
| DNS / HTTPS | 既存ドメイン・ACM | 初期はALBのDNS名によるHTTP確認。機密データは扱わない |
| RDS / SES / Redis | 構築対象 | 後続拡張。初期構築では作成しない |
| IAM | 学習用の広い権限を含む | 操作・対象リソースを用途別に限定 |
| 削除 | 元ラボの削除スクリプト | 対象スタックを指定したCDKによる削除と残存確認 |

元設計をすべて実装したものではなく、下記の段階別範囲を本ラボの基準とする。

## 3. 構築段階

| 段階 | 内容 | 完了確認 |
| --- | --- | --- |
| 0 | ローカル準備・初回build / synth | 実施済み。詳細は導入記録を参照 |
| 1 | dev用ネットワーク・Web基盤をCDKで構築 | 差分確認、デプロイ、ALB経由の応答、削除 |
| 2 | CodeBuild / CodeDeploy / CodePipeline | コミットからアプリ更新、テスト失敗時の停止、ログ確認 |
| 3 | 本番想定環境・承認・切り戻し | devで確認した同一成果物を承認後に配布し、旧版に戻す |
| 4 | RDS、Rails、S3アップロード、HTTPS等 | 各機能の設計・費用を確認して個別に追加 |

SES、ElastiCache、ECS、オンプレミス連携は初期構築の対象外である。実施する際に本書へ設計を追加する。

## 4. 環境とパラメーター

CDKの環境はAWSアカウントとリージョンの組である。`dev` / `prod-sim`は本ラボ独自のステージ区分であり、同一アカウントでも名前とスタックを分ける。

| 項目 | dev | prod-sim |
| --- | --- | --- |
| 用途 | 最初に構築する検証環境 | 後続で構築する本番想定環境 |
| AWSプロファイル | learning | learning（別アカウント化は未計画） |
| リージョン | ap-northeast-1 | ap-northeast-1 |
| VPC CIDR案 | 10.20.0.0/16 | 10.30.0.0/16 |
| AZ | 1a / 1cを候補とし利用可否を確認 | 同左 |
| Web EC2 | 2台、t3.microを初期候補 | 同左 |
| NAT Gateway | 各AZに1台、計2台 | 同左 |
| アプリポート | 3000 | 3000 |
| ログ保持期間案 | 7日 | 7日 |

アカウントIDは認証済みプロファイルから解決し、ソースに直書きしない。CIDRは元設計から変更した候補値であり、既存VPCとの重複を確認して確定する。
ステージ、CIDR、AZ、台数、インスタンスタイプ、管理接続元CIDR等を型付き設定としてまとめる。秘密情報は設定ファイルやcontextに保存しない。
物理名を指定する場合はステージを含める。S3等はグローバル一意性が必要なため、単純な固定名を避ける。

### サブネット案

| 用途 | AZ | dev | prod-sim |
| --- | --- | --- | --- |
| Public 01 | 1a | 10.20.0.0/20 | 10.30.0.0/20 |
| Public 02 | 1c | 10.20.16.0/20 | 10.30.16.0/20 |
| Private 01 | 1a | 10.20.64.0/20 | 10.30.64.0/20 |
| Private 02 | 1c | 10.20.80.0/20 | 10.30.80.0/20 |

明示したCIDRを再現する場合、CDKの自動サブネット割当結果を前提にせず、生成テンプレートでCIDRとルートを確認する。

## 5. ネットワーク・Web基盤

- Public Subnetにinternet-facing ALB、NAT Gateway、踏み台EC2を配置する。
- Private SubnetにWeb EC2を各AZ1台配置し、Public IPは付与しない。
- PublicのデフォルトルートはIGW、Privateのデフォルトルートは同一AZのNAT Gatewayとする。
- ALBはHTTP 80を受け、Target GroupのHTTP 3000へ転送する。ヘルスチェックは`/`とする。
- WebはAmazon Linux 2023のx86_64 AMIを候補とし、アプリ実行環境とCodeDeploy Agentの対応状況を実装前に確認する。
- 踏み台はt3.microを候補とする。SSH鍵は利用可能なKey Pairを確認してパラメーターで指定し、秘密鍵をリポジトリへ格納しない。
- 初期アプリはリリース識別子を返す小さなHTTPサービスとする。使用言語、プロセス起動方法、配置先は実装前に確定する。

### Security Group

| 対象 | インバウンド | 許可元 |
| --- | --- | --- |
| ALB | TCP 80 | 0.0.0.0/0 |
| Bastion | TCP 22 | 作業者のグローバルIP /32 |
| Web | TCP 22 | Bastion SG |
| Web | TCP 3000 | ALB SG |

外向き通信はパッケージ取得、成果物取得、CodeDeploy、ログ送信等に必要となる。初期はNAT経由を設計案とし、必要な通信先・権限を確認する。SSHをCI/CDの配布経路には使用しない。

## 6. CDK管理方針

基盤用スタックとパイプライン用スタックを分ける案とする。実装時にスタックID、依存関係、削除順序を確定する。
TypeScriptコードをCloudFormationテンプレートへ合成し、`diff`で確認してから対象スタックをデプロイする。
`synth`の成功だけではデプロイ権限やリソース作成成功を確認したことにならない。

CDK bootstrapのアカウント・リージョンと既存スタックを確認する。bootstrapが作成するS3、ECR、IAMロール等はアプリ用リソースと区別し、共有利用の有無を確認する。

既存Terraform管理リソースをCDKから変更・削除しない。参照が必要な場合は参照のみであることと管理元を明示する。
手動構築が必要なリソースは理由・設定値・削除手順を記録する。現時点では手動構築必須の対象は特定していない。

## 7. CI/CD設計案

```text
作業ブランチ → Pull Request → レビュー → main
                                         ↓
                                 CodePipeline
                                         ↓
                            CodeBuild（テスト・成果物作成）
                                         ↓
                            CodeDeploy（devのEC2へ配布）
                                         ↓
                               動作確認・手動承認
                                         ↓
                         CodeDeploy（prod-simへ同一成果物配布）
```

初期ソースは既存GitHubリポジトリとする案で、AWSとの接続はCodeConnectionsによる方式を実装時に確認する。CodeCommitは別途比較検証する候補とし、初期の二重管理は行わない。
最初はdevへのパイプラインのみ構築する。基盤のCDKデプロイとアプリ配布は別操作とし、アプリ変更が自動で基盤を変更する構成にはしない。

### buildspec.yml

CodeBuildで実行する依存関係導入、テスト、成果物作成を記述する。バージョン0.2を使用する案とし、具体的なコマンドとビルドイメージはアプリ選定時に確定する。
成果物にはアプリ、`appspec.yml`、デプロイ用スクリプト、リリース識別子を含める。テスト失敗を無視して後続デプロイに進む処理は組み込まない。

### appspec.yml

EC2向けCodeDeployを初期対象とする。`appspec.yml`を配布成果物のルートに配置し、ファイル配置先、権限、ライフサイクルフックを定義する。
初期方式はインプレース更新を候補とし、アプリ停止、配置、起動、応答確認のスクリプトを作成する。Agent導入と成果物取得に必要なIAM権限・ネットワーク到達性を準備する。
Deployment Groupはステージ別タグで対象EC2を限定する。ALB連携、更新単位、ヘルス条件、失敗時の切り戻し条件を確定してから配布する。

### 成果物と切り戻し

パイプライン専用S3バケットを使用し、既存アプリのS3とは分ける。公開アクセスを禁止し、保存時暗号化、保持期間、削除方針を設定する。
成功した旧リビジョンを保持し、失敗検知と旧リビジョンへの再デプロイを検証する。アプリ切り戻しでDB変更まで戻るとは扱わず、初期アプリはDB不要とする。

## 8. Git・レビュー

- `main`は確認済みコードを置くブランチとする。
- 作業は`feature/<内容>`または`fix/<内容>`で行い、Pull Requestに目的、変更点、確認結果を記載する。
- 個人検証では自己レビューであることを明記し、他者レビュー実績と区別する。
- インフラ変更はbuild、テスト、synth、diffを確認する。アプリ変更はアプリテストと配布結果を確認する。
- 本番想定環境への反映は検証済みのGitコミットと成果物を特定して行う。ステージのパラメーターを分けるだけでコードの旧版が自動保持されるとは扱わない。
- `node_modules`、`cdk.out`、認証情報、秘密鍵をGit管理対象に含めない。

## 9. IAM・ログ

| 対象 | 権限・役割の設計方針 |
| --- | --- |
| CDK実行者 / bootstrapロール | 対象環境への基盤デプロイ権限を確認 |
| CodePipeline | ソース接続、対象CodeBuild / CodeDeploy、成果物S3への必要な操作 |
| CodeBuild | 成果物S3、CloudWatch Logs、必要な依存取得等 |
| CodeDeployサービスロール | 対象EC2の識別、採用するALB連携等に必要な操作 |
| Web EC2ロール | 成果物取得、Agent、ログ送信等に必要な操作 |

IAMの具体的なAction / Resourceは採用機能に合わせて確定する。`AmazonS3FullAccess`を元設計からそのまま転用しない。
ビルドログ、デプロイ履歴、Agentログ、アプリログを調査対象とする。保存先、ログ保持期間、通知先は構築時に明確にする。

## 10. 検証・費用・削除

| 検証 | 確認内容 |
| --- | --- |
| 基盤 | CIDR、ルート、SG、Private EC2、ALB到達、対象環境 |
| パラメーター変更 | diffが意図した環境・リソースだけに出ること |
| 正常デプロイ | コミット・成果物・配布結果・HTTP応答の対応 |
| 異常系 | テスト失敗、フック失敗、ログ調査、旧版への切り戻し |
| 削除 | スタック、EC2、ALB、NAT、EIP、保存データ等の残存 |

NAT Gateway 2台、ALB、EC2、ストレージ、ビルド実行、パイプライン、ログ等は費用確認の対象とする。無料で利用できる前提を置かない。prod-simは必要な検証時のみ構築する。
費用上NAT台数等を変える場合は、本書のパラメーターと経路設計を更新してから実装する。

終了時は自動実行を止め、必要な成果物・ログを確認し、依存関係に従って対象スタックを削除する。S3内データ、保持指定リソース、bootstrap資産が残る場合があるため、削除成功だけで残存なしと判断しない。
元ラボの`cleanup_all.sh`や`terraform destroy`をこのCDK環境の削除に使用しない。

## 11. 実装前の確定事項

- アカウント確認、利用可能AZ、既存CIDR・名前との重複確認。
- CDKステージ指定方法、スタック分割、bootstrapの要否と必要権限。
- Webアプリの言語・起動方式、AMI、Key Pair、管理接続元。
- CodeDeploy Agent、ALB連携、配布方式、切り戻し条件。
- GitHub接続、CodeBuildイメージ、成果物の保持・削除・暗号化設定。
- 料金確認と、後続機能を含めた構築対象範囲。
